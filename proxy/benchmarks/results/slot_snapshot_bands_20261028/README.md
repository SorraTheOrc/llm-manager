## Reading the numbers

- **Populate before save is mandatory for these numbers.** Without it the save captures an almost-empty slot, so `snapshot_bytes` and `cached_tokens` say nothing about a prompt-sized session. Both runs here use `--populate-slot`, with the measured slot pinned.
- **`cached_tokens` cannot separate a restored KV from llama-server's RAM prompt cache** (`--cache-ram`): both surface as a small `timings.prompt_n`. The token metric proves the prefix was not recomputed; the *latency* comparison against the adaptive timeout is what decides whether the band benefits inside the cap.
- **"Under load" is one concurrent stream** pinned to the other slot. It reproduces "saves issue while another slot is processing", not the full production contention mix (that is the bake-off replay).
- **Measurements bypass the proxy.** Save/restore go straight to llama-server, so `session_slot_skip_when_busy`, the context cap, the dispatch lease and the failure cooldown are *not* in the measured path; the replay/log-analysis children cover those exclusions.
- **Timeout attribution matters.** A wall-clock timeout is reported next to llama-server's own `timings.save_ms`/`restore_ms`. Where the gap is the whole budget, the operation waited for a busy server (another slot's prefill), which is a *scheduling* limit rather than a snapshot-mechanism limit.

## Fidelity caveats

Recorded explicitly, following the convention of `docs/slot-count-verdict-lp-0mv9ungeb009xuz5.md`: a number is only usable once the condition it was taken under is stated.

- **No mode lock is held.** Save/restore are issued straight at llama-server; the run takes no mode-switch lock (`LP-0MVCBMLP7009MN81`). A mode switch during the window restarts the backend and would void the affected band, so the time each band was measured is recorded above (`Runs` table) for correlation against the proxy log. It is a recording, not a protection.
- **No live dispatch lease is taken.** The proxy's per-endpoint dispatch lease / slot-ownership registry is not consulted and cannot see this harness, so a live session can be dispatched onto the measured slot mid-band. Nothing here proves the host was quiet; the `queued s` column in *Timeout attribution* is the observable that exposes such interference (wall clock above the server's own `save_ms`/`restore_ms`).
- **The measured slot is destroyed.** `--populate-slot` erases and then prefills the measured slot, so any live session that owned that slot loses its cached KV and re-prefills on return. That is a real cost of measuring on the production host, not a neutral probe.
- **Instance ports churn; the router port does not.** The runs above address `base_url` = `http://127.0.0.1:8080`. On the production host the per-model llama-server instances are recycled by the router onto new ephemeral ports, so a direct instance URL goes stale mid-investigation; slot actions therefore carry the model name and go through the router, which is also the path the proxy itself uses.
