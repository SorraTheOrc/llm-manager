# ubatch-size 1024 → 2048: A/B measured and REVERTED (LP-0MVIQ0FSX006HQOS)

Part of epic **LP-0MVIPY7QX0027XVD** (minimise local LLM tail latency).
Date: 2026-10-22. Host: Strix Halo (gfx1151), 120 GB GPU.

## Why this was tried

Prefill is effectively the whole local response time
(`dispatch_to_first_byte` ≈ total): the epic baseline measured llama-server
prompt-eval durations p50 16 s, p90 189 s, max 591 s, at 77–302 t/s. llama.cpp
scales prompt processing with the *physical* micro-batch (`--ubatch-size`) while
the workload stays compute-bound, and 1024 was conservative for a 120 GB GPU
running `--batch-size 8192`.

## Method

`scripts/ubatch_ab_benchmark.py` — measures llama-server's own reported
`timings.prompt_per_second` (prompt-eval throughput) for fixed prompt sizes.
Two details matter for validity:

- **Unique prompt text per repetition plus `cache_prompt: false`.** An identical
  prompt is served from llama.cpp's slot prompt cache, which reports a
  near-zero prompt-eval time and silently makes the A/B meaningless (the first,
  discarded run of this benchmark hit exactly that).
- **Three repetitions per size**, p50/p90 reported; the epic's headline metric
  is prompt-eval t/s over **20k+ token** batches.

Command (both arms, identical workload):

```bash
python3 scripts/ubatch_ab_benchmark.py --base-url http://localhost:8080 \
  --model Qwen3 --sizes 8192,16384,24576 --reps 3 \
  --label <baseline-1024|candidate-2048> --out <file>.json
```

The change required a llama-server restart, which also empties the 40 GiB
prompt cache. That does not bias these numbers (unique prompts, cache
disabled per request), but it does mean the surrounding *proxy* first-byte
stats were cold for ~an hour and must not be compared across the restart.

## Results (prompt-eval throughput, t/s)

| Prompt | ubatch 1024 p50 / p90 | ubatch 2048 p50 / p90 | p90 gain |
|---|---:|---:|---:|
| ~8.9k tokens | 506.6 / 511.8 | 232.7 / 475.9 | 0.93× (noisy¹) |
| ~17.9k tokens | 208.8 / 213.3 | 341.9 / 345.2 | **1.62×** |
| ~26.8k tokens (20k+ headline) | 240.8 / 241.1 | 247.5 / 250.3 | **1.04×** |

¹ the 2048 arm produced one pathological 97.4 t/s sample at ~8.9k tokens
(TTS shares this GPU, which is explicitly out of scope for this item), so the
small-bucket comparison is not reliable in either direction.

Raw data: `benchmark-results/ubatch-ab-2026-10-22-baseline-1024.json` and
`benchmark-results/ubatch-ab-2026-10-22-candidate-2048.json`.

## Decision: reverted

The item's gate is **≥1.3× at p90** over the 20k+ batches that dominate the
local tail. Measured **1.04×** → **fail**. The 1.62× win exists but is confined
to the ~18k compute-bound band; at ~27k the prefill is memory-bandwidth bound
on this GPU, which is exactly the risk the item recorded ("Throughput may be
memory-bandwidth bound already … if so the gain will be small — AC2 is the fail
gate").

Because the local tail is driven by 40–80k-token prefills (sessions reach
170k+), a micro-batch increase that buys nothing at 27k is not worth the
restart, the extra activation VRAM, or the small-prompt variance. `models.ini`
`[Qwen3]` and `start-llama.sh` are both back at **1024**, with a comment
recording this result so the experiment is not repeated blindly.

VRAM was checked during the candidate arm: no OOM, llama-server started cleanly
and the proxy reported `healthy` with all three services up.

## If this is revisited

Measure at **40k–80k tokens**, the regime that actually produces the
minutes-long first-byte stalls. If prefill is memory-bandwidth bound there, a
larger micro-batch will not help and the levers are elsewhere (prefill
serialisation, ETA-based refusal, deadline detour — all landed in this epic).
